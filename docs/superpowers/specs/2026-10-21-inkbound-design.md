## 1. 意圖與動機

使用者早年玩過網頁 RPG《WOG》（PHP + MySQL，2010 年代），最喜歡的是**持續掛機升級、看著角色成長，然後通過更難的關卡**。當年遊戲沒有自動放置，要靠外掛軟體掛機。

這次要做一款**自己風格的新遊戲**，而不是 WOG 的移植：

- 把「掛機成長＋推關」做成正式的**放置玩法**。
- 加入 Path of Exile 式的**天賦搭配與裝備詞綴**，讓玩家能研究並嘗試不同 build。這是使用者在 PoE 最喜歡的兩件事之一。另一件是「打到稀有大獎」，見 §4.6。
- 題材與畫面換成**水墨修仙**，修仙為主、武俠為輔。〔使用者決定〕
- 同時是使用者**學習 .NET** 的專案。使用者平常不寫 .NET，但看過自己 WealthOS 專案的 .NET 後端結構。〔使用者決定〕

WOG 原始碼（`~/Project/WOG4.5_Releas_CT`）只當作氣氛參考，**不移植任何程式、數值或內容**。原作有著作權聲明，禁止修改與商業使用。

### 玩家與遊玩節奏

- 第一階段**只給使用者自己玩**，之後可能開放給朋友。〔使用者決定〕
- 平常**偶爾上線看一下、收成果**；有空時會**花一段時間研究**經脈與法寶搭配。〔使用者決定〕

## 2. 目標、非目標、反目標

**目標**
- 單人放置修仙 RPG：自動戰鬥、推關、境界成長、離線收益。
- 經脈圖（天賦）＋法寶銘文（詞綴）能組出多種可行流派，並有「搭配起來突然變很強」的時刻。
- 手機直式優先的響應式網頁，電腦上也能玩。
- 水墨風格，關鍵時刻用華麗特效打破素雅。

**非目標（第一版不做，但架構不能擋路）**
- 多人內容：宗門／公會、交易、論劍／PK、排行榜。使用者認為可以後期再補。〔使用者決定〕
- 渡劫飛升（轉生），見 §4.9。
- build 分享代碼（給朋友匯入）。
- 寵物／御靈、合成、任務系統。
- 原生 App 上架（之後用 Capacitor 包裝網頁）。
- 雲端部署。

**反目標（就算能跑也算失敗）**
- **美術風格很差**，而且畫風不一致的 AI 圖到處都是。這是使用者唯一明確擔心的事，對策見 §5.3。
- 變成 WOG 的照搬。使用者明確表示不想完全照搬。
- 數值只是一直變大，沒有 build 的差異和研究空間。

## 3. 核心循環

1. 角色在目前關卡**自動戰鬥**，獲得修為（經驗）、靈石（金錢）、法寶與通貨。
2. 修為累積後**提升境界**，屬性成長，並獲得經脈點數。
3. 玩家**選擇功法與心法**、用點數**打通經脈穴位**、**更換法寶**、用通貨**洗煉法寶銘文**，讓 build 成形。
4. 推進關卡，每卷最後是 **Boss**。打不過就留在可以打的關卡繼續累積，變強後再挑戰。
5. 離線期間繼續累積，上線時**一次結算**並顯示「離開期間獲得了⋯⋯」。

## 4. 遊戲系統

以下具體名稱、數量與數值都是方向示例，最終內容由實作時的內容設計決定（見 §9）。

### 4.1 境界（等級）

- 大境界依序為練氣、築基、金丹、元嬰、化神⋯⋯每個大境界再分若干層。
- 第一版做到**化神左右**即可。〔Claude 的判斷〕
- 突破大境界時有專屬演出（書法大字＋特效）。
- 數值曲線必須為 §4.9 渡劫飛升預留空間：後期成長要能放緩，讓「重來換永久加成」有吸引力。

### 4.2 歷練（關卡）

- 世界以**卷**為單位，每卷是一個區域（例如冷峰寒地），卷內有若干關，最後一關是 Boss。
- 一般關卡無限循環：同一關的妖怪會一直出現，玩家在這裡掛機。
- 挑戰 Boss 成功就解鎖下一卷；失敗則回到該卷最後一個一般關卡繼續掛機。
- 提供「自動推進」開關：勝率夠高時自動往下一關，打不過就自動退回。〔Claude 的判斷〕

### 4.3 經脈圖（天賦樹）

- 對應 PoE 的天賦樹：一張**人體經脈與穴位的網狀圖**。穴位就是節點，打通穴位就是點天賦，必須從已打通的穴位相鄰延伸。
- 不同經脈區域代表不同流派。第一版做 **3～4 個流派**，例如劍修、符修、體修、毒修。〔Claude 的判斷〕
- 節點分三種：小穴位（小幅加成）、大穴位（較大加成）、**關鍵穴位**（改變機制，例如「會心時引爆所有劍意」）。
- **洗點便宜**，鼓勵嘗試。
- 手機上要能縮放和拖曳瀏覽。

### 4.4 法寶與銘文（裝備與詞綴）

- 對應 PoE 的裝備詞綴系統。法寶有部位（例如兵器、護身、佩飾等，部位數由實作決定），有稀有度，例如凡品、靈品、寶品、仙品、傳說。
- 法寶身上有隨機的**銘文**（詞綴），稀有度越高，詞綴越多或越強。
- **傳說法寶是固定設計的特殊法寶**，會改變玩法並開啟新 build，例如「飛劍繼承你的會心率」。這是單人遊戲裡「大獎」的主要來源。
- 一鍵換上更好的、一鍵分解多餘的（分解得到素材或通貨）。

### 4.5 通貨（洗煉材料）

- 對應 PoE 的各種石頭：丹藥、符籙、靈石等，各有改造法寶的功能，例如重洗全部銘文、新增一條銘文、提升品質、升級稀有度。
- 稀有通貨的意義是「有機會把一件好法寶變成神器」，沒有交易也有價值。

### 4.6 大獎的意義（沒有交易時）

- 傳說法寶要能改變玩法，不能只是數值較高。
- 稀有通貨能讓玩家自己做出神器。
- 稀有的功法或心法秘笈能開啟新玩法。
- **掉落演出要華麗**：稀有物品掉落時有專屬光柱、印章和畫面效果，戰報中醒目標示。

### 4.7 功法（主動招式）〔使用者決定：功法系統，類似 PoE 技能寶石的精簡版〕

- 角色的**出手方式由功法決定**。build 的骨架是三者互相搭配：**功法決定怎麼打，經脈與法寶強化它**。
- **主功法**：同時裝備 1 個，決定攻擊機制，例如劍氣、符籙爆裂、毒霧持續傷害、飛劍。主功法帶有標籤（例如劍、符、毒、持續、範圍），經脈與銘文依標籤生效，例如「劍類功法傷害 +20%」。
- **心法**：同時裝備 2 個，改造主功法，例如「劍氣分裂成三道，各造成 60% 傷害」「毒的持續時間加倍」。心法只對符合標籤的主功法有效。
- 功法與心法的**秘笈靠掉落取得**，學會後永久擁有，可以自由切換。稀有秘笈也是「大獎」的來源之一。
- 第一版規模：每個流派約 2 個主功法，心法合計約 10 個。〔Claude 的判斷〕
- 開局時提供一個基礎主功法，確保新角色能戰鬥。

### 4.8 build 存檔

- 可以存幾套「功法＋心法＋經脈＋法寶」組合，快速切換。
- 資料格式要能日後匯出成分享代碼。分享功能本身不在第一版。

### 4.9 渡劫飛升（轉生）— 預留，第一版不實作

- 修到頂後渡天劫，成功就飛升到下一界：境界重置，保留永久的「仙緣」加成。
- 第一版只需要確保資料模型和數值曲線不擋路。〔Claude 的判斷；使用者對第一版是否要有未明確表態，以「之後再說」處理〕

### 4.10 離線收益

- 上線時伺服器依照離開的時間結算修為、靈石和掉落，並顯示摘要。
- 離線結算有上限時數，具體上限由實作決定。〔Claude 的判斷〕

## 5. 畫面與美術

### 5.1 整體風格〔使用者決定：水墨東方〕

- 宣紙底色、墨色筆觸、朱紅點綴；字體用書法或楷體類，例如霞鶩文楷、馬善政體這類免費字型。
- **平時素雅，關鍵時刻炸開**：大招、會心、稀有掉落、境界突破時，用金色劍氣、朱紅雷劫、潑墨爆開、蓋章式字樣製造強烈反差。
- 手機直式優先；電腦上同一套版面，置中或適度放寬。
- 遊戲名「墨渡」的標誌用書法字，搭配朱紅印章。〔使用者決定〕

### 5.2 歷練主畫面〔使用者決定：文字戰報＋立繪對戰的混合〕

- **上半部是對戰舞台**：遠山水墨背景，左邊是玩家、右邊是妖怪，都是靜態立繪；平時輕微呼吸晃動，受擊時抖動。特效（劍氣、潑墨、傷害數字、「會心」印章）疊在舞台上。
- **下半部是戰報**：逐行出現的文字，最新在下、舊的往上淡出；有分頁可以篩選「全部／掉落／觸發」，讓玩家看得到經脈和銘文確實觸發。
- 頂部顯示境界、靈石、卷與關卡；底部是導覽列，暫定：歷練、本命（角色）、經脈、行囊（法寶）。
- 參考樣稿：`docs/superpowers/mockups/battle-v2.html`，以瀏覽器開啟（水墨手機版，左為有立繪、右為無立繪）。同目錄的 `visual-style.html` 是四種風格的比較（使用者選了 D 水墨東方），`battle-presentation.html` 是三種戰鬥呈現的比較（使用者選了 A＋C 混合）。實作時以 `battle-v2.html` 作為主畫面的視覺驗收基準。
- 第一版戰鬥一律**一對一**：玩家對一隻妖怪。飛劍、符籙等是玩家攻擊的表現與效果，不是場上可被攻擊的獨立單位。〔Claude 的判斷〕

### 5.3 美術來源與缺圖退路

- 美術用 **AI 生圖**，**由使用者自己生圖**。〔使用者決定用 AI；由誰生是 Claude 的判斷〕實作方要提供一份**圖檔規格**（尺寸、去背、webp、檔名即內容 id）和**生圖提示詞範本**（含水墨風格描述與「附上風格基準圖」的做法）。建議使用者先產出幾張滿意的風格基準圖，之後生圖時都附上基準圖，以維持一致。
- **第一版的完成標準不包含美術**：全部以書法字退路呈現也算完成。〔Claude 的判斷〕
- **設計原則：就算一張插圖都沒有，遊戲也要好看。** 風格主要靠字體、版面、配色和特效撐起來。
- **缺圖退路**：某個妖怪或角色沒有立繪時，舞台上自動改顯示**直書的書法名字**，特效照樣打在字上，版面不變。開發初期可以全部用這種方式。
- 角色只用靜態圖，動態由程式處理（晃動、殘影、墨跡），不畫逐格動畫。
- 前端以內容 id 對應圖檔，例如 `art/<id>.webp`；圖不存在就走退路。

### 6.3 關鍵決定：規則在後端，前端只負責播放事件〔Claude 的判斷，使用者未反對〕

- **所有遊戲規則都在 C# 的 Domain 層**，包括戰鬥模擬、功法與心法效果、傷害公式、觸發判定、掉落與詞綴生成、經驗與境界。前端不做任何規則計算。
- 伺服器每次推進歷練時，回傳一串**戰鬥事件**，例如出招、傷害（含是否會心）、穴位或銘文觸發、妖怪死亡、掉落、升級。每個事件帶有相對時間。
- 前端拿同一串事件，**同時**驅動舞台特效和戰報文字，兩邊因此永遠一致。
- 理由：
  1. 使用者想學 .NET，遊戲的核心應該用 C# 寫；
  2. 離線結算本來就要在伺服器做；
  3. 日後開放給朋友時，數值不會被前端竄改。

### 6.4 放置推進模型〔Claude 的判斷〕

- 每個角色記錄「上次結算時間」。
- **線上時**：前端定期（例如每 10 秒）呼叫推進 API。伺服器模擬從上次結算到現在的戰鬥，回傳這段期間的事件；前端照事件的時間軸播放。畫面會比伺服器晚一個週期，換來看起來連續的戰鬥。
- **離線回來時**：呼叫同一個 API，但經過時間很長。此時不逐場模擬，而是用統計方式快速結算（每場平均收益乘以場數，掉落依機率抽），只回傳摘要和最後幾場的事件。
- 戰鬥模擬使用**可指定種子的亂數**，讓測試可以重現。
- 推進間隔、離線上限與統計結算的精確做法由實作決定，但要符合上述行為。

### 6.5 內容資料

- 妖怪、法寶、銘文池、傳說法寶、功法、心法、經脈圖、關卡等都是 `backend/content/` 下的 JSON 資料，**調數值或加內容不用改 C#**。
- 只有後端讀取；前端要顯示名稱與說明時透過 API 取得。
- 每筆內容有穩定的英文 id（例如 `snow-demon`），前端用 id 對應美術圖。
- 測試使用獨立的小型內容資料，不受正式數值調整影響。

### 6.6 資料庫與版本控制〔使用者決定：MySQL、Flyway、Database-First〕

- 資料表結構**只由 Flyway migration 決定**，沿用使用者在 `~/Project/fantasy-system/game-server` 的慣例：
  - 檔名 `V<9 位數版本號>__<英文描述>.sql`，例如 `V000000001__create_player_table.sql`；
  - `db/ddl/` 放結構變更，`db/dml/` 放資料變更，兩者共用一條版本號序列；
  - 已套用的 migration 不得修改，要改就新增一個版本。
- **SQL 安全檢查**：比照 game-server 的 `scan_sql.sh`，擋下含 `DROP TABLE`、`DROP VIEW`、`DROP DATABASE`、`TRUNCATE` 的 migration。納入提交前的檢查。〔Claude 的判斷〕
- **Database-First 流程**：
  1. 手寫 migration；
  2. Flyway 套用到本機 MySQL；
  3. 執行 `scripts/scaffold-db.sh`（包裝 `dotnet ef dbcontext scaffold`）重新產生 Infrastructure 的 model 與 DbContext；
  4. 產生的檔案一起 commit。
- 產生的檔案**不得手改**；需要擴充時寫在另一個檔案的 `partial class`。〔Claude 的判斷〕
- scaffold 產生的 model 只代表「資料庫長怎樣」，**只存在於 Infrastructure 層**。Domain 層有自己的遊戲模型，兩者在 Application 層轉換。這樣資料表變動不會直接波及戰鬥規則，Domain 測試也不需要資料庫。〔Claude 的判斷〕
- 遊戲內容（§6.5）仍是 JSON 檔，不放進資料庫；資料庫只存玩家狀態，例如帳號、角色、背包、經脈、build、進度。〔Claude 的判斷〕

### 6.7 執行與部署〔Claude 的判斷〕

- **開發時**：MySQL 和 Flyway 用 `docker compose` 開，啟動 MySQL 8 並自動套用所有 migration。後端在本機用 `dotnet watch` 跑，前端用 `pnpm dev`。使用者的電腦已有 Docker。
- 使用者電腦目前只有 .NET 9 SDK，開工前需安裝 .NET 10 SDK。
- **執行時**在使用者自己的 Mac 上跑。〔使用者決定〕docker compose 另提供一個「完整」設定，包含 MySQL、Flyway、API 與前端靜態檔，資料存在 volume，一個指令就能常駐。
- 手機在同一個 Wi-Fi 下以電腦的區網 IP 連線遊玩；要從外面連時再考慮 Tailscale 之類的工具。
- 雲端部署之後再說。〔使用者決定〕

## 7. 開發方式

- 依使用者的全域規則：TDD（一次一個測試）、結構性與行為性變更分開 commit、小而頻繁的 commit、commit 訊息用英文 Conventional Commits 加 emoji。
- 資料庫變更的順序：先寫 migration，再 scaffold，再寫用到它的程式與測試。
- 使用者正在學 .NET：實作時在關鍵處說明 C# 和 ASP.NET Core 的概念。
- 規劃、說明、文件用中文；程式碼註解語言由專案 CLAUDE.md 決定，未規定時用中文。
